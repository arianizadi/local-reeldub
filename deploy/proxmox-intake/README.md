# Private VPN intake on Proxmox

The dedicated unprivileged Debian 13 container fetches public Instagram Reels and inspects uploads. Clients use mutual TLS on TCP 8443. The media process runs with a separate Unix identity and has no access to the VPN key, TLS key, accounts, database or job ledger. The firewall permits public HTTPS and DNS only over the VPN. Its physical interface permits the VPN's exact endpoint, DHCP, and replies to approved private client addresses.

## Installation

1. Create an unprivileged LXC with an independent LAN address, 2 CPUs, 1536 MiB memory, an 8 GiB system disk and `--dev0 /dev/net/tun`. Reserve its address. The guest has no inbound public port or router forwarding. Provide packages before enabling the egress policy. Debian packages are `ca-certificates curl openssl python3-venv ffmpeg openvpn nftables nginx-light`. Install the versions of FastAPI, Uvicorn and yt-dlp pinned in the repository's service requirements and intake Dockerfile into `/opt/reeldub-venv`.
2. Run `bash install-storage.sh GUEST_ID ZFS_POOL` on the Proxmox host. This creates an AES-256-GCM ZFS dataset and attaches it at `/srv/reeldub-private`. A second encrypted dataset at `/var/lib/reeldub-private/intake-issuer` is visible only to host management. The unlock key is a mode-0600 file on the separate Proxmox system disk. Back up the key separately from the encrypted dataset. A host administrator can access both.
3. Copy this directory and the five Python files `server/{__init__,intake,download,media_network,source}.py` to the same relative locations under `/opt/reeldub-intake`. Stream the provider zip into `python3 deploy/proxmox-intake/stage-profile.py /srv/reeldub-private/vpn` inside the guest. It rebuilds an OpenVPN profile from the embedded credentials and validated public IPv4/UDP endpoint. It accepts the supported inline certificate format and ignores external hooks and routes in provider archives.
4. On management run `bash certificates.sh authority /var/lib/reeldub-private/intake-issuer`. Generate the intake's server CSR inside the guest using `bash certificates.sh request server /srv/reeldub-private/tls reeldub-intake.internal`. On each approved caller generate a dedicated CSR using `bash certificates.sh request client ENCRYPTED_CLIENT_DIR CLIENT_NAME`. Sign public CSRs on management with `bash certificates.sh sign ISSUER_DIR server GUEST_IP` or `bash certificates.sh sign ISSUER_DIR client`. Both read a CSR from stdin and return the public certificate on stdout. Install the server certificate as `tls/server.pem`, the client certificate as `client.pem`, and the public CA as `ca.pem` on each endpoint. Set private directory and key permissions for the calling service. Before activating the listener, register the issued client's public certificate inside intake using `python3 permit-client.py allow client.pem`.
5. On Proxmox run `python3 host-guard.py GUEST_ID GUEST_IP GATEWAY_IPV4 COORDINATOR_IPV4`. On stdin supply one line with the original VPN server's public IPv4 address and UDP port from the trusted profile. The generated rules attach only to this guest's veth. The guard's isolated kernel probe confirms interface binding survives creation and recreation on the running kernel. Its runtime marker is mounted read-only as guest mp1; the intake firewall requires that marker at startup. The gateway is also the DHCP server in this network. This deployment expects stable on-link caller, guest and gateway addresses.
6. In the guest run `bash install-guest.sh COORDINATOR_IPV4`. The separate proxy user can reach only public HTTPS and the designated DNS resolver through the VPN. The parser and downloader user can reach the proxy on loopback, with no direct Internet path. Staged media has its own 2 GiB encrypted filesystem. The signing authority reserves separate space for certificate maintenance. For live updates, drain active requests and pass `--drained` before the caller addresses to apply the new service settings. Enable Proxmox guest autostart after verifying its boot. Configure the calling API with `REELDUB_INTAKE_URL=https://GUEST_IP:8443`, `REELDUB_INTAKE_CA`, `REELDUB_INTAKE_CERT` and `REELDUB_INTAKE_KEY`. GPU workers consume centrally staged inputs.

For renewal, generate a fresh key and CSR in a new directory and repeat the signing steps. Register the new client serial, copy the existing public CA into that staging directory, then run `python3 activate-client.py ACTIVE_DIR STAGED_DIR` on the client. The atomic swap preserves the old directory for rollback. Revoke the old serial with `python3 permit-client.py revoke serial:HEX_SERIAL` or supply the old certificate file. When a client key is suspected compromised, revoke immediately and generate a fresh key before re-enrolling. The listener reloads the allowlist. Replace a renewed server certificate only after verifying its private key, SAN and chain. Reload `reeldub-intake-mtls` and test from the caller. `openssl x509 -checkend 2592000 -noout -in CERT` checks whether a leaf has at least thirty days remaining. The signing tool records serial, subject and expiry in the host-only issuer directory.

## Acceptance checks

From the permitted caller, `curl --cacert ca.pem --cert client.pem --key client.key https://GUEST_IP:8443/live` checks the private listener. An authenticated `POST /inspect` with a small MP4 exercises the parser. An authenticated `POST /reel` with a public Instagram Reel must return a playable video and an `X-Duration` header. Check that a connection without a client certificate fails.

Before admitting live traffic, verify the parser user cannot reach a literal public IP while the VPN is up. Verify the proxy user can reach a known public HTTPS endpoint through `tun0`. Stop `reeldub-intake-vpn` in the new guest and repeat from the proxy user. It must now fail while the physical interface is available. The private LAN management port must also be unreachable. Restart the VPN, confirm `ip route get 1.1.1.1` selects `tun0`, then reboot only this guest and rerun the authenticated Reel test.

Persistent credentials and the temporary media spool occupy separate encrypted ZFS datasets. On startup the intake service verifies the spool's dataset identity before clearing abandoned files. An unavailable spool stops the service. Intake removes each download when delivery finishes. Stage verified maintenance packages into the guest through Proxmox management so its forwarding and outbound policies remain in place.
